# Billing and abuse controls

## First-party authentication

Authentication uses the `auth_users_v1`, `auth_sessions_v1`, and `auth_tokens_v1` collections. Startup creates their unique and TTL indexes before marking MongoDB ready. Authentication actions fail closed when MongoDB is unavailable; development in-memory optimization mode does not create auth accounts or sessions.

Passwords use Argon2id (64 MiB memory, three iterations, one lane). Access JWTs are HS256 only, limited to ten minutes, and validated against configured issuer and audience. The browser keeps access tokens in React memory. Refresh tokens are random opaque values stored only as SHA-256 hashes in MongoDB and in a `HttpOnly` cookie; refresh rotates the token and a detected token replay revokes its session. Sessions expire after 30 days of inactivity. Password reset revokes all sessions.

Cookie-based refresh/logout operations require an exact allowed `Origin` and a CSRF header bound to the refresh token. Production cross-site deployments must use HTTPS and configure `AUTH_COOKIE_SAME_SITE=none`; a custom frontend/API domain arrangement under the same site is preferred. CORS must list the exact frontend origin and allow credentials.

Registration, email verification, forgot-password, and reset-password flows require SMTP settings plus `APP_ORIGIN`. Without a complete mail configuration, registration and recovery return a service-unavailable response and do not claim an email was sent. Verification and reset tokens are single-use, expire, and are stored only as hashes. Email links carry tokens in URL fragments so browser HTTP requests do not send the token to the application server.

The old demo records are not migrated or deleted. New account IDs are generated by MongoDB and do not match old Clerk subject strings, so old optimization/payment records cannot be read or grant new entitlements. No collection cleanup is performed by application startup.

## Plan policy

The shared policy is in `../shared/planPolicy.js` and is used by the API and pricing page.

- Free: 3 successful optimizations, 1 successful bullet rewrite, and 3 history records per UTC calendar month. Cover letters require Pro.
- Monthly Pro: one-time ₹299 purchase for 30 days.
- Annual Pro: one-time ₹2,388 purchase for 365 days.
- Paid access does not renew automatically. A new order is rejected while Pro access is active.

Quota reservations are incremented atomically before work starts and released when validation, provider, or persistence fails. Monthly counters expire after the month boundary. Successful work remains counted.

## MongoDB deployment

Production requires MongoDB. Startup creates indexes for the new, versioned `payment_ledger_v1` and `abuse_counters_v1` collections before marking the database ready. The payment ledger has unique Razorpay order and sparse unique payment indexes. The abuse counter has a unique counter key and TTL index. A duplicate-data/index error prevents production startup; no existing optimization collection is changed.

Payment verification updates one ledger document from `created` to `captured`. That atomic state transition is the entitlement grant; duplicate callbacks observe the existing captured record. Provider timeouts leave the order ungranted and can be retried. No webhook endpoint exists in this product; refunds and chargebacks therefore do not revoke access automatically.

## Rate limiting and proxy configuration

Mongo-backed fixed-window counters coordinate rate limits across backend instances. Current policy: 5 uploads per IP per 15 minutes, 10 AI requests per user per minute, 5 payment orders per user per 10 minutes, and 10 verification requests per user per 10 minutes. All limits return HTTP 429 with `Retry-After` and a structured error.

For deployments behind a reverse proxy, set `TRUST_PROXY_HOPS` to the exact number of trusted proxy hops. Leave it at `0` when clients connect directly. Only set a nonzero value when the edge proxy strips/overwrites forwarded-IP headers and the backend cannot be reached around that proxy.

When `NODE_ENV` is not production and MongoDB is unavailable, counters use process memory for development only. They reset on restart and do not coordinate across instances. Production counter and entitlement reads fail closed when MongoDB is unavailable.

## Document parsing

Uploads are limited to 10 MiB, one multipart file, no extra fields, and five attempts per IP per 15 minutes. DOCX central-directory checks cap entries, individual and total expanded sizes, and compression ratio. PDF and DOCX parsing runs in workers with a 128 MiB old-generation limit, two concurrent workers per process, and a 15-second timeout. These process-local parser slots do not coordinate across instances; retain edge request limits and monitor worker restarts.
